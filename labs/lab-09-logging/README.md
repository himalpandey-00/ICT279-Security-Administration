# ICT279 Lab 09 – Windows and Linux Logging

## Overview

This lab explored logging as part of secure server and security administration. The practical work covered Windows Event Logging, Linux logging, log archiving and export, and live network monitoring with `netstat`.

The lab environment used a Windows domain controller (`HP-DC`), a Windows 10 domain client (`WIN10`), and an Ubuntu Linux virtual machine.

---

## Task 1 – Event Logging (Windows)

### 1. Remote Event Log Management

On the Windows 10 client, the Windows Defender Firewall advanced settings were opened and the **Remote Event Log Management** inbound rules were enabled. This allows Event Viewer to support remote event-log access.

![Remote Event Log Management firewall rules](screenshots/01-remote-event-log-firewall-rules.png)

### 2. Allow Log On Locally

The **Default Domain Policy** was edited under:

`Computer Configuration > Policies > Windows Settings > Security Settings > Local Policies > User Rights Assignment`

The **Allow log on locally** policy was configured while retaining the Administrators group and allowing an ordinary domain user to perform the logon tests.

![Allow log on locally policy](screenshots/02-allow-logon-locally-policy.png)

### 3. Advanced Audit Policy

Advanced auditing was configured under:

`Computer Configuration > Policies > Windows Settings > Security Settings > Advanced Audit Policy Configuration > Audit Policies`

The required areas were configured for:

- Account Logon – Credential Validation
- Account Management – User Account Management
- Account Management – Security Group Management
- Logon/Logoff – Account Lockout
- Logon/Logoff – Logoff
- Logon/Logoff – Logon

The relevant categories then appeared as configured.

![Advanced audit policy configured](screenshots/03-advanced-audit-policy-configured.png)

The policy was applied with:

```powershell
gpupdate /force
```

![Group Policy update](screenshots/04-group-policy-update.png)

## Windows Logon and Logoff Events

### Failed Logon – Event ID 4625

A deliberately incorrect password was entered to generate a failed interactive logon. Event Viewer recorded:

- **Event ID:** 4625
- **Description:** An account failed to log on
- **Logon Type:** 2
- **Failure reason:** Unknown user name or bad password
- **Account tested:** Himal
- **Log:** Windows Logs > Security on the Windows 10 client

This demonstrated that the failed interactive logon was recorded on the computer where the access attempt occurred.

![Failed logon Event 4625](screenshots/05-failed-logon-event-4625.png)

### Successful Interactive Logon – Event ID 4624

A successful interactive console logon was identified as:

- **Event ID:** 4624

- **Logon Type:** 2

Logon Type 2 represents an interactive logon at the computer console.

![Successful interactive logon](screenshots/06-successful-logon-event-4624-type2.png)

![Logon failures custom view](screenshots/11-logon-failures-custom-view.png)

## Archiving Windows Event Logs

### Event Viewer Archive

The filtered logon-failure events were saved in `.evtx` format and reopened in Event Viewer under Saved Logs.

The archived file represents a snapshot of the saved events rather than a live event log.

![Archived logon failures](screenshots/12-archived-logon-failures-evtx.png)

### Command-Line Export and Archive

The Windows `wevtutil` utility was also used to export and archive the Security log.

```powershell
wevtutil epl Security SecurityLogArchive.evtx
wevtutil al SecurityLogArchive.evtx
```

`wevtutil epl` exported the event log, while `wevtutil al` created a self-contained archive.

![wevtutil archive](screenshots/13-wevtutil-security-log-archive.png)

### Text Export

The filtered failed-logon events were exported as a text file:

`FilteredAuditFailuresLog.txt`

The text representation makes event fields easy to review without Event Viewer.

![Filtered audit failures text export](screenshots/14-filtered-audit-failures-text-export.png)

## Task 2 – Event Logging (Linux)

### Linux System Logs

On Ubuntu, `/var/log` was inspected. The system contained `/var/log/syslog` together with rotated historical log files.

Recent entries were examined using:

```bash
sudo tail -n 30 /var/log/syslog
```

![Linux syslog](screenshots/15-linux-syslog.png)

### Last Boot Messages

The last system boot was checked with:

```bash
who -b
```

Boot messages were then examined using:

```bash
journalctl -b | head -n 30
```

The output showed early boot information including kernel initialization and VirtualBox virtual hardware information.

![Linux last boot logs](screenshots/16-linux-last-boot-logs.png)

### Authentication Logs

Ubuntu authentication activity was examined through:

```text
/var/log/auth.log
```

Controlled authentication attempts were generated using `su - himal`, including an incorrect password and a successful authentication.

The authentication log contained PAM authentication information and a failed `su` record.

```bash
sudo tail -n 40 /var/log/auth.log
```

![Linux authentication logs](screenshots/17-linux-authentication-logs.png)

## Apache Logging

Apache logs were located under:

```text
/var/log/apache2/
```

The directory included files such as:

- `access.log` – HTTP access/request information
- `error.log` – Apache errors, warnings, startup and operational messages
- `other_vhosts_access.log` – access information associated with other virtual hosts
- rotated historical log files

![Apache log files](screenshots/18-apache-log-files.png)

The Apache site configuration was checked for the logging directives:

```bash
grep -R "CustomLog\|ErrorLog" /etc/apache2/sites-enabled/
```

The configuration showed directives similar to:

```apache
ErrorLog ${APACHE_LOG_DIR}/error.log
CustomLog ${APACHE_LOG_DIR}/access.log combined
```

These directives determine the Apache error and access logging destinations and configuration.

## Task 3 – Using netstat

### Ethernet and Protocol Statistics

On the Windows domain controller, the following command was used:

```powershell
netstat -e -s
```

This displayed Ethernet statistics together with protocol statistics.

![netstat Ethernet and protocol statistics](screenshots/20-netstat-ethernet-protocol-statistics.png)

### Listening TCP Ports

Listening TCP ports and their process IDs were examined using:

```powershell
netstat -ano -p tcp | findstr "LISTENING"
```

Notable ports observed on the domain controller included:

| Port | Service/Purpose |
|---:|---|
| 53 | DNS |
| 88 | Kerberos |
| 135 | RPC Endpoint Mapper |
| 139 | NetBIOS Session Service |
| 389 | LDAP |
| 445 | SMB |
| 464 | Kerberos password change |
| 636 | LDAPS |
| 3268 | Active Directory Global Catalog |
| 3269 | Active Directory Global Catalog over SSL/TLS |

The server also had higher dynamic/RPC listening ports.

![Listening TCP ports](screenshots/21-netstat-listening-tcp-ports.png)

### DNS Server Process ID

Port 53 was observed listening on the domain controller with **PID 2904**. The PID was verified with:

```powershell
tasklist /FI "PID eq 2904"
```

The result identified:

```text
dns.exe    PID 2904
```

UDP port 53 was also associated with PID 2904.

Therefore, in this lab environment, the Windows DNS Server process was **`dns.exe` with PID `2904`**.

![DNS Server PID](screenshots/22-dns-server-pid-2904.png)

## Key Findings

This lab demonstrated how Windows and Linux provide different mechanisms for collecting and reviewing security-relevant events. Windows Event Viewer and Advanced Audit Policy provide detailed records of authentication and account activity, while Ubuntu uses log files such as `syslog` and `auth.log` together with the system journal.

The exercises also demonstrated the importance of filtering and archiving logs. Windows Custom Views can isolate relevant security events, while `.evtx`, text export, and `wevtutil` provide different methods of preserving event information.

Finally, `netstat` showed how live network information can complement event logs by identifying active/listening services and mapping network ports to process IDs.
